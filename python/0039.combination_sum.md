# 39. Combination Sum

The backtracking code is mind-fuck yet genius! 

```python
class Solution:
    def combinationSum(self, candidates, target):
        def dfs(start, path, target):
            if target == 0:
                # If we've reached the target, add the current path to results
                # Important: using list() to create a copy
                result.append(list(path))
                return
            for i in range(start, len(candidates)):
                if candidates[i] > target:
                    # No need to continue if the candidate exceeds the target
                    break
                # Include the candidate and continue searching
                path.append(candidates[i])
                dfs(i, path, target - candidates[i])
                path.pop()
        
        candidates.sort()  # Sort candidates to improve efficiency
        result = []
        dfs(0, [], target)
        return result

# Example usage:
solution = Solution()
candidates = [2, 3, 6, 7]
target = 7
print("Combinations:", solution.combinationSum(candidates, target))
# Output: [[2, 2, 3], [7]]
```

---

## Why `result.append(list(path))` and Not Just `result.append(path)`?

This is a **critical** detail that many people misunderstand. The key issue is **reference vs copy**.

**The Problem Without `list()`:**

When you do `result.append(path)`, you're appending a **reference** to the `path` list, not a copy of its contents.

```python
result = []
path = [2, 3]
result.append(path)      # Append REFERENCE to path
print(result)            # [[2, 3]]

# Now modify path
path.pop()              # Remove 3
path.append(5)          # Add 5
print(result)           # [[2, 5]] ← CHANGED! (Should be [[2, 3]])
```

**Why?** Because `path` and `result[0]` point to the **same list object in memory**. When you modify `path`, the changes reflect in `result[0]` because they're the same object!

---

**The Solution: `list(path)` Creates a Copy**

When you do `result.append(list(path))`, you're creating a **new independent copy** of `path`.

```python
result = []
path = [2, 3]
result.append(list(path))    # Append a COPY of path
print(result)                # [[2, 3]]

# Now modify path
path.pop()                   # Remove 3
path.append(5)               # Add 5
print(result)                # [[2, 3]] ← UNCHANGED! (Correct!)
```

Now `result[0]` is a different object from `path`. Modifying `path` doesn't affect the stored combination.

---

**In Combination Sum Context:**

In the backtracking algorithm, the same `path` list is reused throughout the recursion:

```python
def dfs(start, path, target):
    if target == 0:
        result.append(list(path))  # Copy the current state of path
        return
    
    for i in range(start, len(candidates)):
        path.append(candidates[i])
        dfs(i, path, target - candidates[i])
        path.pop()  # Backtrack: remove the candidate we just added
```

Each time we find a valid combination (target == 0), we must **snapshot** the current state of `path` because:
1. The `path` list will be modified in future recursive calls
2. Without copying, all combinations would end up pointing to the final state of `path`
3. `list(path)` creates an independent copy that stays frozen with its original values

**Visual Example of What Goes Wrong Without `list()`:**

```
Recursion tree (candidates=[2,3], target=5):

dfs(start=0, path=[], target=5)
  ├─ i=0: path=[2]
  │  └─ dfs(start=0, path=[2], target=3)
  │     ├─ i=0: path=[2,2]
  │     │  └─ dfs(start=0, path=[2,2], target=1)
  │     │     └─ No valid combinations, backtrack
  │     │
  │     └─ i=1: path=[2,3]
  │        └─ dfs(start=1, path=[2,3], target=0)
  │           └─ WITHOUT list(): result.append(path)  ← Stores REFERENCE
  │              └─ Returns, but path still = [2,3]
  │
  └─ i=1: path=[3]
     └─ dfs(start=1, path=[3], target=2)
        ├─ i=1: path=[3,3]
        │  └─ dfs(start=1, path=[3,3], target=-1)
        │     └─ Returns, backtrack: path=[3]
        └─ Returns, backtrack: path=[]

Final result WITHOUT list():
[reference to [3], reference to [3], ...]
↑ All point to the same FINAL state of path!

Final result WITH list():
[[2, 3], [3], ...]
↑ Each is an independent COPY of path at that moment
```

**Other Ways to Copy (all equivalent):**

```python
result.append(list(path))           # Method 1: list() constructor
result.append(path[:])              # Method 2: slicing
result.append(path.copy())          # Method 3: .copy() method
result.append([*path])              # Method 4: unpacking
```

All create independent copies. `list(path)` is the most common and explicit.

## Time & Space Complexity

**Tight Bound (Accurate):**
- **Time**: O(N^(T/M)) where N = number of candidates, T = target, M = minimum candidate value
  - Maximum recursion depth = T/M (if we keep picking the smallest element)
  - At each level, we branch into up to N recursive calls
  - Total nodes in tree ≈ N^(T/M)

- **Space**: O(T/M) for recursion stack and path array (excluding output storage)
  - Output space: O(C × T/M) where C = number of valid combinations

**Loose Upper Bound (For Interviews if Unsure):**
- **Time**: O(N^T) — assumes depth T instead of T/M (conservative but safer)
- **Space**: O(T) — ignoring output storage

**Key Insight:** When M is large (larger minimum), T/M gets smaller, so complexity improves significantly. Tight bound reflects this; loose bound doesn't.

**Concrete Examples:**
- `[2, 3], target=10`: O(2^5 × 5) = O(160) tight vs O(2^10) = O(1024) loose
- `[1], target=5`: O(1^5) = O(5) — actually linear, not exponential!
- `[5, 10, 15], target=50`: O(3^10 × 10) ≈ O(600K) tight vs O(3^50) ≈ O(10^24) loose

**Interview Strategy:**
- State tight bound first if confident: "O(N^(T/M)) time"
- If questioned on derivation, explain recursion depth = T/M and branching = N
- Can fall back to loose bound: "worst case O(N^T) time"

## The Core Question: How Does the Same Number Get Used Unlimited Times?

This is **the most important concept** to understand in this problem. Many people get confused when they see `for i in range(start, len(candidates))` and think: *"Wait, if we restrict to `start`, how can we reuse the same number?"*

**The answer is subtle but crucial:** `start` prevents revisiting earlier candidates *in the same loop level*, but it does **NOT** prevent revisiting the *same index* across *different recursive calls* (different tree depths).

### The Magic: `dfs(i, ...)` vs `dfs(i+1, ...)`

**When you pass `i` (not `i+1`) to the recursive call**, you allow that same index to be picked again in the next recursion level.

```
dfs(start=0, path=[], target=7)
  ↓
  Pick index 0 (value=2), add to path
  ↓
  dfs(start=0, path=[2], target=5)  ← Same start=0! Can pick index 0 again
    ↓
    Pick index 0 (value=2) AGAIN!
    ↓
    dfs(start=0, path=[2,2], target=3)  ← Still start=0! Can pick index 0 again
      ↓
      Pick index 1 (value=3)
      ↓
      dfs(start=1, path=[2,2,3], target=0)
        ↓
        target==0 ✓ Add [2,2,3] to result
```

### Visual Comparison: Unlimited vs No Reuse

**Unlimited Reuse (What Combination Sum Does):**
```
Pick index 0 (value=2)
  ↓ Call dfs(start=0, ...)
  └─→ Can pick index 0 again? YES ✓
      Pick index 0 (value=2) again
        ↓ Call dfs(start=0, ...)
        └─→ Can pick index 0 again? YES ✓
            Keep going...
```

**No Reuse (Like Combinations II):**
```
Pick index 0 (value=2)
  ↓ Call dfs(start=1, ...)  ← start moved to 1
  └─→ Can pick index 0 again? NO ✗
      Only pick from index 1 onward
        ↓ Call dfs(start=2, ...)  ← start moved to 2
        └─→ Only pick from index 2 onward
```

### Code-Level Explanation with Execution Trace

Let's trace with `candidates = [2, 3]` and `target = 5`:

```python
# Recursive calls in order:
dfs(start=0, path=[], target=5)
│
├─ i=0: candidates[0]=2
│  path.append(2)  → path=[2]
│  dfs(start=0, path=[2], target=3)  ← Notice: start=0, NOT 1
│  │
│  ├─ i=0: candidates[0]=2 AGAIN!
│  │  path.append(2)  → path=[2,2]
│  │  dfs(start=0, path=[2,2], target=1)
│  │  │
│  │  ├─ i=0: candidates[0]=2 AGAIN!
│  │  │  path.append(2)  → path=[2,2,2]
│  │  │  dfs(start=0, path=[2,2,2], target=-1)
│  │  │  │
│  │  │  └─ target < 0? Nope, just return. target is -1. Backtrack.
│  │  │
│  │  ├─ i=1: candidates[1]=3
│  │  │  path.append(3)  → path=[2,2,3]
│  │  │  dfs(start=1, path=[2,2,3], target=-2)
│  │  │  │
│  │  │  └─ target < 0? Nope, just return. Backtrack.
│  │  │
│  │  path.pop()  ← backtrack
│  │
│  ├─ i=1: candidates[1]=3
│  │  path.append(3)  → path=[2,3]
│  │  dfs(start=1, path=[2,3], target=0)
│  │  │
│  │  └─ target==0? YES! Add [2,3] to result. Return.
│  │
│  path.pop()  ← backtrack
│
├─ i=1: candidates[1]=3
│  path.append(3)  → path=[3]
│  dfs(start=1, path=[3], target=2)
│  │
│  ├─ i=1: candidates[1]=3
│  │  path.append(3)  → path=[3,3]
│  │  dfs(start=1, path=[3,3], target=-1)
│  │  │
│  │  └─ target < 0? Return. Backtrack.
│  │
│  path.pop()  ← backtrack
│
RESULT: [[2, 3]]
```

**Key observations:**
1. In the first `dfs(start=0, ...)` call, we iterate `for i in range(0, 2)` — indices 0 and 1.
2. When we pick index 0 (value=2), we call `dfs(start=0, ...)` again.
3. In this nested call, we **again** iterate `for i in range(0, 2)` — the loop resets to include index 0.
4. This allows picking index 0 multiple times across different tree levels.

## Understanding the `path.pop()` Mystery

We have the example `[2, 3, 6, 7]`. When we call `dfs(i, path, target - candidates[i])`, it means we are including the candidate that `i` is pointing to. For simplicity, let's assume `i = 2`, which means it points to `6`. 

This means there will be a DFS run where `6` is part of the `path`, and we already do the `target - candidates[i]` when we initiate the DFS.

What you need to understand is that the DFS run above is **separate**! That run will execute independently, and we don't need to worry about it in the current context. 

After initiating this DFS that includes `6`, we proceed to **skip** the `6` in our current `path`. This is exactly what the code `path.pop()` is doing. We remove the `6` from `path`, adding or removing from the `path` does not affect the logic functionality in any way, `path` variable is just there to add accepted answer to result. 

After doing the `path.pop()`, the magic happens when we go back to the loop. The loop increments `i`, so now `i = 3`, which points towards `7`.

Since we removed the `6` from `path` previously, and we only *initiated* the DFS using `dfs(i, path, target - candidates[i])` when `6` was included, our original `target` remains unchanged in this context. Notice how we did not alter the `target` before — by doing `target - candidates[i]` while calling DFS, we just *initiated* a new DFS with a new `target` *if* `6` were included.

Now, the `path` may look like `[2, 3]` because we removed `6`. When we execute `path.append(candidates[i])`, we add `7`, making the `path` `[2, 3, 7]`. This `path` variable is basically used to build combinations to add into the result; it doesn't affect the actual function or logic of the algorithm. The **core** of the algorithm and code lies in the call `dfs(i, path, target - candidates[i])`, where we do not modify the original `target` variable but instead *initiate* a new instance of DFS with the adjusted `target` if we choose to include a candidate.

---

## Explanation of Approach:

1. **Sorting the Candidates**: We sort the candidates array to enhance efficiency. This allows us to stop further exploration as soon as we encounter a candidate that exceeds the current target.
   
2. **Base Case**: If the target becomes zero, we add the current path to the results as it represents a valid combination.
   
3. **Backtracking**: We add a candidate to the current path and recursively explore further by reducing the target. After exploring, we remove the last candidate (backtrack) and try the next candidate.

4. **Key Detail: Reusing the Same Index**: By passing `i` (not `i+1`) to the recursive call, we allow the same index to be selected multiple times across different recursion depths, enabling unlimited reuse of each number.

```
Start: target=7, path=[], start=0

Level 0 (start=0)
├─ Pick i=0 (val=2) → path=[2], target=5
│  │

│     ├─ Pick i=0 (val=2) → path=[2,2], target=3
│     │  │
│     │  └─ Level 2 (start=0)  ← Can still pick from index 0
│     │     ├─ Pick i=0 (val=2) → path=[2,2,2], target=1
│     │     │  └─ target < 0 with any candidate, backtrack
│     │     │
│     │     ├─ Pick i=1 (val=3) → path=[2,2,3], target=0 ✓ FOUND
│     │     │  (start=0 means we can pick from [2,3,6,7], but we pick 3)
│     │     │
│     │     ├─ Pick i=2 (val=6) → target < 0, backtrack
│     │     └─ Pick i=3 (val=7) → target < 0, backtrack
│     │
│     ├─ Pick i=1 (val=3) → path=[2,3], target=2
│     │  └─ Level 3 (start=1)  ← NOW we skip index 0!
│     │     ├─ Pick i=1 (val=3) → target < 0, backtrack
│     │     ├─ Pick i=2 (val=6) → target < 0, backtrack
│     │     └─ Pick i=3 (val=7) → target < 0, backtrack
│     │
│     ├─ Pick i=2 (val=6) → target < 0, backtrack
│     └─ Pick i=3 (val=7) → target < 0, backtrack
│
├─ Pick i=1 (val=3) → path=[3], target=4
│  └─ Level 1 (start=1)  ← Now we skip index 0!
│     ├─ Pick i=1 (val=3) → path=[3,3], target=1
│     │  └─ target < 0 with any candidate ≥ index 1, backtrack
│     │
│     ├─ Pick i=2 (val=6) → target < 0, backtrack
│     └─ Pick i=3 (val=7) → target < 0, backtrack
│
├─ Pick i=2 (val=6) → target < 0, backtrack
└─ Pick i=3 (val=7) → path=[7], target=0 ✓ FOUND

RESULT: [[2,2,3], [7]]
         ↑ No duplicates!
```

**Key insight:** By maintaining and incrementing `start`, we ensure non-decreasing order. A number can repeat (because `start` doesn't increment), but [2,3,2] cannot occur (because once we move past index 0, we stay at index 1 or beyond).

## Summary of Key Points

1. **`start` parameter controls ORDER, not REUSE**
   - `start` prevents going backward in the array
   - `start` does NOT prevent reusing the same index in deeper levels
   
2. **Why `dfs(i, ...)` instead of `dfs(i+1, ...)`?**
   - `dfs(i, ...)`: Next level can still pick from index `i` onward → element can repeat
   - `dfs(i+1, ...)`: Next level skips index `i` → element cannot repeat
   
3. **How sorting helps:**
   - Enables early termination with `break` when `candidates[i] > target`
   - Without sorting, we'd need to check all remaining candidates
   
4. **Why `path.pop()` is necessary:**
   - `path` is used to track the current combination being built
   - We only add to result when `target == 0`
   - Backtracking restores `path` to explore alternate combinations at the same level
   
5. **Backtracking pattern:**
   ```
   path.append(candidate)      # Try including this candidate
   dfs(...)                    # Explore recursively
   path.pop()                  # Undo the choice, try next candidate
   ```

---

## Conclusion

The Combination Sum problem elegantly uses the `start` parameter to enforce non-decreasing order while allowing unlimited reuse via passing the same index to recursive calls. This is the sweet spot between efficiency and correctness: we get unique combinations (no duplicates), avoid permutations, and don't need post-processing cleanup. The sorted array enables early pruning, making the algorithm practical even for larger inputs.
